## 猜测板块

### 概述

处理对某张符卡为哪位创作者的猜测，是项目的核心功能板块。

### 核心数据结构

#### 符卡—创作者对应表

- **格式**：扁平树状结构，按 `Boss → 符卡 → 创作者对应条目` 排列。
- **说明**：记录每个 Boss 下每张符卡对应的创作者，创作者栏可为空（表示尚未揭晓）。
- **数据模型**：嵌套结构，Boss 包含 `List<SpellCard>`，使用 Godot Tree 控件展示。
- **符卡编号**：Boss 内独立编号，从 1 开始。猜测时组织者通过下拉框选择当前 Boss，猜测文本中的符卡下标针对该 Boss。
- **编辑规则**：
  - Boss 名称和符卡名称均可编辑。
  - 创作者栏仅支持从别名表主名中下拉选择。
  - 添加/删除 Boss 和符卡通过按钮操作。

#### 创作者别名表

- **格式**：树状结构（嵌套），一行一个创作者。
  - 父行：**主名**，用于功能的显示或处理。
  - 子行：**别名**，每个创作者可有任意多个，用于处理猜测文本中的非主名称呼。
  - 没有别名的创作者只有父行，编辑器中标注为「无别名」。

#### 猜测文本

- **严格格式**：`<spellcard-id><creator> <spellcard-id><creator> ...`
  - 每个 `符卡下标—创作者对` 以空格分隔，符卡下标为数字，创作者为字符串，两者紧邻。
  - 示例：`1Alice 2Bob 3Charlie`

### 功能需求

#### 导入符卡—创作者对应表

| 导入方式       | 说明                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------- |
| 从工程文件读入 | 自动检测 Sharp 编辑器生成的 LuaSTG 工程文件中的符卡，创作者栏留空。**暂不实现**，UI 预留禁用按钮。 |
| 从表读入       | 支持 CSV 和 Excel 格式。格式：`Boss, 符卡名, 创作者`（三列，创作者可为空）。                       |

导入失败时弹窗提示具体错误（格式不对、列缺失、编码问题等）。

#### 编辑符卡—创作者对应表

- 可视化编辑符卡栏和创作者栏。
- 支持添加和删除条目（通过按钮操作）。

#### 导入创作者别名表

- 仅支持从表导入（CSV / Excel）。
- 格式：`主名, 别名1, 别名2, ...`（第一列主名，后续列为不定长别名）。
- 导入失败时弹窗提示具体错误。

#### 编辑创作者别名表

- 支持完整 CRUD（创建、读取、更新、删除）。
- 主名行与别名子行均可就地编辑，编辑只影响被编辑的那一行。
- 「添加别名」作用于选中的创作者（选中的是它的别名子行时同样算）；未选中任何行时弹窗提示并中止。
- 「删除选中」对主名行删除整个创作者，对别名子行只删除该条别名。

#### 处理猜测文本

- **输入**：一个或多个猜测文本（严格格式）。
- **处理管道**：手动输入和群聊抓取走同一处理管道。
- **已揭晓符卡**：跳过不参与判断，回应中注明已揭晓。猜测符卡数仅计未揭晓的符卡。
- **回应规则**（策略模式，`IGuessResponseHandler` 接口，可替换）：

| 猜测符卡数 | 回应                   |
| ---------- | ---------------------- |
| ≥ 3 张     | 返回猜对的个数         |
| = 2 张     | 全对回"对"，有错回"错" |
| ≤ 1 张     | 不回应                 |

### 扩展功能

#### 模糊化处理

- **前提**：需配置 AI 模型。未配置时按钮禁用，hover 提示"请先配置 AI 模型"。
- **功能**：接收非严格格式的猜测文本，由 AI 模型转换为严格格式。
  - AI 提示词结构：别名表 + 符卡列表在前，猜测文本在末尾（利用缓存命中）。
  - 自动将别名转换为创作者主名（依据别名表）。
  - 系统提示词内含一条「别名 → 主名」的示范，并说明本身已是主名的名字保持不变；该示范只在别名表非空时给出。
  - 别名表中不存在的别名，由 AI 模型推断对应主名。
  - 别名表为空时，完全依赖 AI 推断。
- **异常处理**：处理失败时返回错误并通知用户。
- **非猜测输入处理**：AI 提示词要求对不像猜测的输入返回固定标记 `NOT_A_GUESS`，程序识别后不回复。

#### 自动抓取群聊猜测文本

- **前提**：需安装群聊机器人框架与服务。
- **支持框架**：Koishi v4。
- **实现方式**：通过 Koishi 插件实现框架与项目通信。插件仅做消息转发，所有处理在 AutoCMEX 完成。插件代码放在 `src/plugin/koishi/`。
- **安装方式**：一键复制插件文件夹到 Koishi 工作区的 `external/adapter-autocmex/`（目录名 = 包短名，与工作区链接同名，覆盖安装即生效），再在控制台「插件配置 → 右键 → 添加插件」搜 `adapter-autocmex`（或看「适配器」分类）启用。
- **托管猜测流程**：Koishi 发送 `command: guess` → AutoCMEX 统一判定/处理 → 返回 `ack` + `event: guess_result` → Koishi 回复原消息。
- **Koishi 回复规则**：优先引用原消息回复，失败时降级为普通回复；非猜测文本不回复。
- **连接解耦**：Koishi 未连接时，手动猜测流程仍可正常运作，不受托管链路影响。
- **筛选方式**（用户可配置）：

| 方式                    | 说明                                             |
| ----------------------- | ------------------------------------------------ |
| 仅严格格式匹配          | 仅当群聊消息符合猜测文本严格格式时视为猜测文本。 |
| 仅 AI 模型智能匹配      | 由 AI 模型判断群聊消息是否为猜测文本。           |
| 先严格匹配，未命中再 AI | 先用正则快速筛选，未命中时再调用 AI 判断。       |

### UI 布局

猜测板块 UI 分为三栏：

| 区域      | 位置     | 内容                                                   |
| --------- | -------- | ------------------------------------------------------ |
| Boss 选择 | 顶部     | 下拉框选择当前被猜测的 Boss，默认选中第一个            |
| 左上      | 左侧上方 | 符卡—创作者对应表（Tree 控件，仅显示当前 Boss 的符卡） |
| 左下      | 左侧下方 | 创作者别名表                                           |
| 右栏      | 右侧     | 上方为猜测文本输入框，下方为回应显示栏                 |

左上和左下之间为可拖拽分割线（VSplitContainer）。功能按钮放置在对应栏目旁。

## 信息板块

### 概述

作品整合完成后，组织者需要把猜测所需的公开信息发到活动群聊。信息板块提供四类信息的展示与发布：符卡 GIF 集、符卡猜测情况表、创作者剩余未被猜测符卡数表、活动规则。

四类信息各自独立成栏，均可单独发布，也可在下栏勾选目标群聊后一键按固定顺序全部转发。

### 功能需求

#### 符卡 GIF 集

- **导入**：支持从文件夹导入，也支持从压缩包导入；两种方式都要求自带清单 json（`manifest.json`），清单逐张记录序号、符卡名、文件名与尺寸。
- **集内自洽校验**：导入时校验清单存在且可解析、清单与目录内图片一一对应（不多不少）、序号唯一、文件名与清单声明一致。任一条不满足即报错并逐条列出原因，**不写入本地数据**（失败不得破坏既有集）。
- **多集管理**：可保存多个集，栏顶下拉切换当前集；切换后卡片列表与发布内容一起切换。
- **展示**：卡片式纵向列表，每张卡片为「`序号. 符卡名`」标题 + 下方动图；列表懒加载，只解码视口内可见的少数几张，避免大体积 GIF 常驻内存。
- **与猜测模块解耦**：符卡名一律取自集内清单，不与猜测表做序号对齐校验（集对应的是导入的工程产物，与当前 Boss 未必同源）。
- **录制**：自动驱动 LuaSTG 引擎逐张录制当前 Boss 的符卡与非符；产物与手工整理的集**同构**（清单 json + `序号.gif`），故复用本栏既有的导入与展示链路。**入口**为本栏既有的「录制」按钮：点击后依次为前置检查 → 手选工程包 zip → 手选输出目录 → 自动跑（带进度与取消），录完**自动导入**并切换为当前集。实施中：引擎侧插件、枚举、批量并行录制与配置入口已完成，`manifest.json` 产出与自动导入在建；引擎启动契约、任务/结果契约与关键设计决策见 `technical-specification.md` 的「符卡 GIF 录制模块」。
- **录制设置**（设置板块「信息」类别页底部，默认折叠）：
  - **引擎目录**：手选或从「整合」板块的 Sharp 目录推断；目录不合法时不保存，并在原处说明原因。
  - **插件状态与部署**：分别展示自家录制插件与第三方弹幕录制器的「已安装并启用 / 已安装但被禁用 / 未安装 / 清单损坏」，并提供「安装并启用」「启用弹幕录制器」「重新检查」；插件清单损坏时不给任何部署动作。未获取第三方录制器时明确提示需自行获取。
  - **并行度**：录制的引擎实例数（1~32），并说明实际并发取「并行度」与「战斗卡数」的较小值、空间不足会自动下调。
  - **沙箱根目录**：每轮为每个 worker 建一份引擎副本，可留空（用系统临时目录）或指定目录（须已存在）；旁注单份占用 × 并行度的估算与所在卷剩余空间，空间不足只预警、不阻止保存。
  - **高级参数**：帧数上限、两个抽帧间隔（首次 / 换挡后重录用：录满被截断或产物 ≥ 30MB 时换第二档）与产物放缩比（10%~100%，默认 50%，决定产物分辨率清晰度与体积），给出间隔与帧率的换算参考，并说明长卡在帧数上限处截断属正常产物。
  - **写入纪律**：未点击任何按钮时对引擎目录零写入；非法值不落盘；改动插件清单前先备份。

#### 符卡猜测情况表

- 取当前 Boss 的全部符卡，三栏：创作者 / 符卡编号 / 符卡名；符卡编号为符卡在该 Boss 内的排列序号（从 1 开始）。
- 已猜出的符卡整行染绿。
- **未猜出的符卡第一栏（创作者）留空**：发布到群聊后不提前泄露答案。
- 发布形式为按内容自适应尺寸的图片。

#### 创作者剩余未被猜测符卡数表

- 按当前 Boss 的创作者分组，逐行给出：创作者 / 符卡总数 / 剩余未被猜出数；总数 = 该创作者名下卡数，剩余 = 总数 − 已猜出数。
- 剩余为 0（全部被猜出）的行整行染绿。
- 发布形式为按内容自适应尺寸的图片。

#### 活动规则

- 纯文本，就地编辑与自动保存，发布时原文发送、不附图片。

#### 目标群聊与发布

- **目标群列表**在设置板块「信息」类别维护（群 ID + 可选展示名 + 启用开关）；「信息」板块下栏的「刷新群列表」向 Koishi 查询群列表并并入本地配置，**新并入的群默认不勾选**。
- 与 Koishi 无连接时「刷新群列表」直接报失败，不静默。
- 各栏自带「发布」按钮，只发布该栏内容。
- 下栏「一键转发」按 **符卡 GIF 集 → 符卡猜测情况表 → 创作者剩余表 → 活动规则** 的固定顺序发布。
- **逐项独立、失败即停**：某一项失败立即停止后续发送，发布报告中显式写明哪些项未被发送（避免看起来像漏发）；报告逐项列出成功/失败与原因。
- 存在失败项时提供「只重试失败项」。
- 发送前做预检（文件存在、可读、非空），避免向群聊发出空图或缺失内容。

### UI 布局

信息板块 UI 分为上栏与下栏，详见「UI 设计」文档：

- **上栏**：四栏横向排布，超出可见宽度可横向滚动；每栏含展示区与「发布」按钮。
- **下栏**：目标群聊多选列表 + 「刷新群列表」+「一键转发」。

## 设置板块

### 概述

显示和修改各板块的配置。

### UI 布局

| 区域   | 位置           | 内容                   |
| ------ | -------------- | ---------------------- |
| 搜索栏 | 顶部，横跨左右 | 用于搜索配置项         |
| 左栏   | 左侧           | 配置类别列表           |
| 右栏   | 右侧           | 当前类别下的具体配置项 |

### 配置分类

配置按板块 + 全局分类，除各板块专属配置外，还需包含以下全局配置：

#### AI 模型配置

- **用途**：供猜测板块的模糊化处理与智能匹配使用。
- **API 格式**：支持 OpenAI 兼容格式和 Anthropic 原生格式。
- **每个模型配置包含**：API 格式、请求地址、模型 ID、API 密钥。
- **安全要求**：API 密钥必须安全保存，绝对不能泄露。
- **数量**：支持配置多个模型。
- **操作**：支持 CRUD，提供"测试连接"按钮验证配置是否正确。

#### 群聊机器人服务配置

- **用途**：配置群聊机器人服务连接。
- **说明**：大部分配置在群聊机器人框架中完成，与本项目无关。
- **连接参数**：WebSocket 端口、模式（Server / Client）、Koishi 地址（Client 模式连接的对端，自动补全 `ws://` 前缀并附 Token）。端口改动即时写回；Koishi 地址在**回车提交或输入框失焦**时写回。
- **模式与实际一致**：Client 模式但 Koishi 地址为空时**不回落成 Server**，启动失败并在 WebSocket 状态面板显式显示「未配置 Koishi 地址」。
- **功能**：支持一键将插件安装到 Koishi 工作区（复制到应用根目录下 `external/adapter-autocmex/`）；已安装的落点路径在设置页回显，重启后仍可见。安装完成后弹窗给出控制台启用路径与检索关键词；缺少工作区链接时提示先跑一次包管理器安装；检测到旧版落点目录 `auto-cmex` 残留时提示移走。
- **可检测性**：控制台的插件检索按**包短名**做子串匹配（短名 = 包名去掉 `koishi-plugin-` 前缀），分类标签取 `koishi.category`。因此插件包名（`koishi-plugin-adapter-autocmex`）、安装目录名、插件自报名三者同为短名 `adapter-autocmex`，并声明 `koishi.category = "adapter"`，保证「添加插件」里搜 `adapter-autocmex` 或直接看「适配器」分类都能找到。
- **支持框架**：目前仅支持 Koishi v4。
