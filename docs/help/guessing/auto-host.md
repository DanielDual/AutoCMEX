# 群聊托管猜测

群聊托管指 Koishi 接收群消息并转发至 AutoCMEX，由后者完成判定并回复原消息。启用前需要完成连接与插件配置；链路、筛选方式与不回复的情形如下。

## 消息链路

群消息先由 Koishi 及已启用的插件转发至 AutoCMEX。AutoCMEX 按当前 Boss、对应表与别名表完成判定，再将结果经同一连接返回，由插件引用原消息回复；引用失败时以普通消息回复。

判定在 AutoCMEX 内完成，插件只负责消息收发。Koishi 停止运行后，手动输入仍可使用，群聊消息不再自动回复。

## 启用条件

1. Koishi v4 运行中，OneBot 适配器（例如 NapCat）已配置，插件已安装并在控制台启用，见 [群聊连接与 Koishi](../settings/chat.md)。
2. 设置 → 群聊中的端口与模式两端一致。
3. [WebSocket 状态面板](../run/websocket.md) 显示已连接。
4. 猜测板块已导入对应表并选择 Boss。

## 消息筛选

筛选方式在设置 → 群聊 →「消息筛选：」中配置，修改后对后续消息生效。

| 筛选方式               | 行为                                | 代价                                  |
| ---------------------- | ----------------------------------- | ------------------------------------- |
| 仅严格格式匹配（默认） | 仅处理符合严格格式的消息，不调用 AI | 不符合格式的消息不处理                |
| 先严格再 AI            | 先按格式匹配，未命中时调用 AI       | 未命中严格格式的消息均调用 AI         |
| 仅 AI 智能匹配         | 每条消息交由 AI 判断                | 每条群消息调用一次 AI，延迟与费用最高 |

默认值为「仅严格格式匹配」。启用托管时可先使用该方式，确认对应表与别名表无误后再调整。

## 不回复的情形

消息不符合猜测格式，或 AI 判定为非猜测文本时，不回复。筛选方式包含 AI 但未配置可用模型时，符合严格格式的消息仍回复，其余不处理。AI 请求最终失败时，消息进入丢包列表且不回复，处理见 [丢包与重试](dropped.md)。未导入对应表或未选择 Boss 时，所有消息均不处理，且不产生丢包记录。

判定成功但有效符卡不足时，回复「必须猜两个以上」，属正常结果，规则见 [猜测文本与回应规则](syntax.md)。

## 与手动输入的关系

Koishi 未连接时，手动输入与「处理」仍可使用。两者的判定规则相同，区别在于输出位置：手动结果仅显示在回应显示栏。

两者共用当前 Boss：群聊消息按「猜测」页选中的 Boss 解析下标，与消息来源无关。

> **注意**：切换 Boss 后，先前发出的群消息仍按旧编号判定。应先切换 Boss，再通知群内成员继续猜测。

## 排查

先查看 WebSocket 状态面板：Client 模式是否已连接、Server 模式是否运行中、连接数是否大于 0。再查看 [日志](../run/logging.md) 中是否收到消息与判定结果。两者均正常时，核对当前 Boss、对应表与「消息筛选」。

Koishi 控制台中找不到插件时，回到设置 → 群聊按安装提示重新安装并启用。
