# AutoCMEX — 技术规格

## 技术栈

| 层级     | 技术                                                                   |
| -------- | ---------------------------------------------------------------------- |
| GUI 框架 | Godot 4.x + .NET 8                                                     |
| 脚本语言 | C#                                                                     |
| UI 方案  | Godot 原生 Control 节点                                                |
| 外部通信 | WebSocket（默认 Server 模式监听端口，也支持 Client 模式主动连 Koishi） |
| 群聊集成 | Koishi v4 插件                                                         |
| 本地存储 | JSON 文件                                                              |
| 加密方案 | AES，密钥文件存放于用户目录                                            |
| 日志     | 文件日志 + 控制台输出                                                  |

## AI 模型集成

### 用途

AI 模型用于猜测板块的以下功能：

| 功能       | 说明                                                           |
| ---------- | -------------------------------------------------------------- |
| 模糊化处理 | 将非严格格式的猜测文本转换为严格格式，并将别名转换为创作者主名 |
| 智能匹配   | 判断群聊消息是否为猜测文本                                     |

### API 格式

支持两种 API 格式：

| 格式               | 说明                                       |
| ------------------ | ------------------------------------------ |
| OpenAI 兼容格式    | `/chat/completions` 端点，适用于大多数厂商 |
| Anthropic 原生格式 | Anthropic Messages API                     |

### 提示词结构

模糊化处理的 AI 提示词按以下顺序组织：

1. 系统提示：任务说明 + 创作者别名表
   - 别名表段含一条「别名 → 主名」的示范，用于演示别名转换规则；没有别名的创作者行标注为「无别名」而不是空括号。别名表为空时，该示范与表头一并省略。
2. 用户消息：猜测文本（放在末尾，利用缓存命中）

### 模型配置项

每个 AI 模型配置包含以下字段：

| 字段     | 说明                                             |
| -------- | ------------------------------------------------ |
| API 格式 | OpenAI 或 Anthropic                              |
| 请求地址 | API 端点 URL                                     |
| 模型 ID  | 模型标识符                                       |
| API 密钥 | 用于认证的密钥                                   |
| 请求超时 | **全局项**（不属于单个模型）：1~600 秒，默认 100 |

除上表的单模型字段外，另有一个**全局**的「请求超时（秒）」设置（1~600，默认 100）：

- 由 `AiServiceFactory.GetActiveService()` 读取并传给 `CreateService(config, timeoutSeconds)`，最终写入服务的 `HttpClient.Timeout`；因此模糊化处理与托管猜测都吃这一项。
- 「测试连接」也跟随该设置，但经 `AiModelConfigPanel.ResolveTestConnectionTimeout()` 取 `min(设置值, 30)`（下限 1 秒），避免一次连通性验证长时间阻塞。

### 安全要求

- **API 密钥必须安全保存，绝对不能泄露。**
- 密钥使用 AES 加密存储，密钥文件存放于用户目录。
- 不得以明文写入日志或显示在 UI 上。
- UI 中密钥字段以掩码形式（`****`）显示。
- 导出配置时排除或加密密钥字段。

### 多模型支持

- 支持配置多个 AI 模型。
- 用户可为不同功能选择不同模型。
- 支持 CRUD 操作。
- 提供"测试连接"按钮验证 API 连通性。

### 异常处理

- AI 调用失败时返回错误并通知用户，不自动重试。
- 未配置 AI 模型时，模糊化处理按钮禁用，hover 提示「请先在设置中选择一个有效的 AI 模型」（运行时由代码设置）。
- 别名表为空时，模糊化处理完全依赖 AI 推断。

## 群聊机器人集成

### 支持框架

Koishi v4。

### 集成方式

通过 Koishi 插件实现框架与 AutoCMEX 之间的 WebSocket 通信，两种模式（设置 → 群聊 → 模式）二选一：

```
┌──────────────┐   WebSocket (JSON)   ┌──────────────┐
│              │ ←──────────────────→ │              │
│   Koishi     │                      │  AutoCMEX    │
│   框架       │   插件仅做消息转发    │  本项目      │
│              │                      │              │
└──────────────┘                      └──────────────┘
```

- **Server 模式**（默认）：AutoCMEX 监听设置里的端口，Koishi 插件作为客户端连入。
- **Client 模式**：AutoCMEX 主动连接设置里的 Koishi 地址（自动补全 `ws://` 前缀并附 Token）。
- 插件仅做消息转发，所有处理逻辑在 AutoCMEX 完成。
- 回应通过同一 WebSocket 连接返回。
- **Client 模式未填 Koishi 地址时不会退化成 Server**：仍按 Client 建立实例，启动失败并把「未配置 Koishi 地址」记进 `IWebSocketServer.LastError`，由状态面板的红色错误行显示——避免「设置写 Client、实际跑 Server」的静默偏差。
- 状态面板显示的**模式、端口/地址、连接数、错误**一律取自实际运行的 `IWebSocketServer` 实例（`Mode` / `Port` / `Url` / `LastError`），不取自设置：设置改动后实例重建前两者可能短暂不一致。

- **单实例单链路**：进程内任一时刻只允许一个 `IWebSocketServer` 实例在工作，一个实例只允许一条链路。实例的创建/启停/重启统一经 `WebSocketLifecycle`：`StopAsync` 一律取消并等待循环退出（不得按「是否已连接」提前返回），`StartAsync` 以「循环是否还活着」判幂等，重启串行化，且**期望配置与当前实例有效配置一致时跳过重建**。原因：配置绑定的 `OnValue` 是**订阅即回调**（启动时模式/端口/地址三个绑定会连打三次重启），若每次重启各建实例而旧的又停不掉，旧实例会成为继续连接的孤儿，对端的「新连接踢旧连接」即演变为连接震颤。
- **停止的可见语义**：`IsRunning` = 已连接（Server 为已监听），`IsActive` = 实例仍在工作（含 Client 的断线重连等待）。状态标签的文案用 `IsRunning` 判定、按钮文案用 `IsActive` 判定——重连等待中若按 `IsRunning` 显示，用户会「点一下反而更连不上、也停不掉」。
- **启停只有一个入口**：界面（状态面板）**不得**自行判方向、也不得对自己的实例引用调 `StartAsync` / `StopAsync`，一律经 `WebSocketLifecycle.ToggleAsync()`——方向在锁内按当前实例判定，与重启共用同一把锁。界面拿的是上次推送的实例引用，配置变更重启期间它可能已指向被替换的旧实例；由界面自行判方向即会出现「旧实例被重新拉起 + 新实例同时在跑」，正是连接震颤的成因。
- **停止后不留任务**：`StopAsync` 返回即代表该实例上再无活动任务。除连接/接受循环外，心跳等派生循环也必须持有自己的句柄并在停止时取消 + 等待退出（心跳还须绑定本次连接的 socket 与令牌，不读共享字段，否则重连后旧心跳会跟着新 socket 继续发 ping）。
- **端口变更**：`StopAsync` 必须真正关掉监听器并等待接受循环退出，否则旧监听器仍占端口，新端口表现为启动失败。

### WebSocket 协议

- **消息格式**：JSON，`id` + `type` + `timestamp` + `payload` 结构。
- **消息类型**：

| type      | 方向              | 说明                       |
| --------- | ----------------- | -------------------------- |
| `command` | Koishi → AutoCMEX | 命令（如 `guess`、`ping`） |
| `event`   | AutoCMEX → Koishi | 事件（如 `guess_result`）  |
| `ack`     | AutoCMEX → Koishi | 命令确认                   |
| `error`   | AutoCMEX → Koishi | 错误响应                   |

- **托管猜测流程**：Koishi 发送 `command: guess` → AutoCMEX 返回 `ack` + `event: guess_result` → Koishi 回复原消息。
- **断线处理**：Koishi 插件自动重连，断开期间消息缓存到内存队列，重连后批量发送。

### 插件说明

- 插件代码放在 `src/plugin/koishi/`。
- 插件维护 `requestId → session` 映射，收到 `guess_result` 事件后优先引用回复，失败降级普通回复。
- **发布内容的群内呈现方式由应用侧决定**：`info_publish_forward` 的 payload 带 `mode` 字段（`forward` = 合并转发一张可展开卡片，`image` = 逐节点各发一条图片消息），插件只照做、不自行判定内容形态；缺省（旧版应用不带该字段）按 `forward` 处理，保证两端版本错配时仍能正常发送。`image` 模式仍受发送前的附件预检约束，发送失败会回报具体原因而不静默回落成合并转发。
- 插件离开本项目无法使用，不对外发布。
- 一键安装：复制插件文件夹到 Koishi 工作区的 `external/adapter-autocmex/`（目录名 = 包短名，与控制台的插件索引名一致；覆盖安装即命中工作区链接指向的目录）。
- 插件包自检口径：`package.json` 的 `main` 直接指向真实入口 `src/index.js`（内容即 CommonJS，无需构建产物，`koishi dev` 与 `koishi start` 行为一致）；`koishi.category = "adapter"` 决定其在控制台「添加插件」里的分类；插件自报名必须等于包短名。

### 消息筛选

用户可在设置中配置筛选方式：

| 方式                    | 说明                                        | 依赖           |
| ----------------------- | ------------------------------------------- | -------------- |
| 仅严格格式匹配          | 正则匹配 `<spellcard-id><creator> ...` 格式 | 无             |
| 仅 AI 模型智能匹配      | AI 判断消息是否为猜测文本                   | 需配置 AI 模型 |
| 先严格匹配，未命中再 AI | 先用正则筛选，未命中时调用 AI               | 需配置 AI 模型 |

## 猜测处理引擎

### 处理管道

手动输入和群聊抓取的猜测文本走统一处理管道：

```
猜测文本 → [模糊化处理(可选)] → 别名转换 → 格式校验 → 匹配对错 → 生成回应
```

### 回应策略

采用策略模式，`IGuessResponseHandler` 接口抽象，便于替换和扩展：

| 猜测符卡数 | 回应                                                                 |
| ---------- | -------------------------------------------------------------------- |
| ≥ 3 张     | 回「猜对/总数」                                                      |
| = 2 张     | 全对回 ✔️，有错回 ❌️                                                |
| ≤ 1 张     | 回「必须猜两个以上」；0 张且全部已猜出回「所有猜测的符卡均已被猜出」 |

- 创作者栏即答案本身，留空表示尚未填写；任何符卡都参与判定，不设「无法判定」状态。
- 已猜出的符卡跳过不参与判断，回应中注明已猜出；回应里的猜测符卡数只计已猜出之外的符卡。

### 丢包与重试

- **落包时机**：严格管道未命中且走 AI 兜底后仍失败（AI 不可用、超时、返回不可解析）时，`GuessProcessingService` 落一条丢包记录，除原文与失败原因外还留档 `requestId`（来源消息标识）、`sender`（发送者）与 `filterMode`（当时的口径）；本地手输路径没有来源，三者存空串而非 null。
- **重放口径**：`RetryDroppedGuessAsync` 按记录里的 `filterMode` 重放，**不读当前设置**——丢包后用户改过筛选模式（如 strict → ai）不该让这条记录永远救不回来。重放**不新落记录、也不删记录**（旧写法是「删旧 + 落新」，用户看到的「丢包被重新解析了一遍」即源于此）。
- **回帖与去留**：重放成功后由 `DroppedGuessRetryService` 用原 `requestId` 经活跃端点推送 `guess_result`（与消息到达链路共用 `GuessReplyFactory`，回帖口径只有一处定义）。去留判据收在协调器一处，按结局分为：
  | 结局 | 含义 | 记录 |
  | ---- | ---- | ---- |
  | `Replied` | 已引用原消息回帖 | 移除 |
  | `NoReplyTarget` | 无来源可回（本地手输产生的丢包） | 移除 |
  | `NoReplyNeeded` | 有来源但按回应策略无需回帖 | 移除 |
  | `NotGuess` | 重放仍未得到有效猜测 | 保留 |
  | `Failed` | 重放报错 | 保留 |
  | `LinkInactive` | 链路未运行 / 没有已连接对端 / 一条都没送出去 / 推送抛异常 | 保留 |
- **送达判据**：`IWebSocketServer.BroadcastAsync` 对单个连接失败只记日志、不抛异常，因此它**返回实际送达的连接数**（客户端链路送出即 1，未连接即 0）；需要「送不出去就保留记录」的调用方必须看这个返回值，不能靠异常判断——否则记录会被删掉，而群里根本没有回复。
- **手动出口**：丢包列表的「重试全部丢包」经协调器逐条重放并把逐条结局显示在回应栏（协调器异常时由面板兜住并提示「重试中断」，按钮状态照常还原）；「删除选中丢包」按选中下标映射到记录 Id 逐条删除，未选中时只提示不动数据。

## 数据存储

### 存储内容

| 数据              | 存储方式          | 格式                                              |
| ----------------- | ----------------- | ------------------------------------------------- |
| 符卡—创作者对应表 | 用户数据目录 JSON | `spellcard_table.json`；导入/导出支持 CSV / Excel |
| 创作者别名表      | 用户数据目录 JSON | `alias_table.json`；导入/导出支持 CSV / Excel     |
| AI 模型配置       | 本地加密存储      | JSON，AES 加密                                    |
| 群聊机器人配置    | 本地配置文件      | JSON                                              |
| 应用设置          | 本地配置文件      | JSON                                              |
| 界面主题          | 本地配置文件      | `app_settings.json` 的 `themeId`，默认 `default`  |
| 录制配置          | 本地配置文件      | JSON                                              |
| UI 布局状态       | 用户数据目录 JSON | `ui_layout.json`；删除即重置布局                  |

### 保存策略

- 自动保存，1-2 秒防抖延迟。
- 用户停止操作后自动写入，无需手动保存。

### 安全原则

1. 敏感信息（API 密钥等）使用 AES 加密存储，密钥文件存放于用户目录。
2. 不得将敏感信息写入日志。
3. 配置文件导出时自动排除敏感字段。

## UI 布局记忆

主窗口几何、各板块分割条与文件选择窗口尺寸都记进 `ui_layout.json`，下次启动或下次弹出时还原。只记**用户真的调过**的项：没调过就不产生记录，一项都没调过时记忆为空、启动行为与旧版一致（文件仍随其它数据一起写出，内容是「没有记录」）。

### 记录内容与语义键

`user://data/ui_layout.json` 是 `DataManager` 的第 8 段数据，复用同一套防抖自动保存、原子写盘与坏文件备份链路，不另起持久化路径。

| 内容         | 字段                              | 说明                                                 |
| ------------ | --------------------------------- | ---------------------------------------------------- |
| 主窗口几何   | 宽 / 高、左上角 X / Y、最大化标志 | 关闭窗口时记录；最大化也记，存的是还原后的普通态矩形 |
| 分割条       | 语义键 + 偏移 + 折叠状态          | 固定 7 条语义键，见下表                              |
| 文件选择窗口 | 宽 / 高                           | 所有文件选择窗口共用一份                             |

分割条的语义键由 UI 层定义、模型只存取不解释，固定 7 条，与场景一一对应：

| 语义键             | 所在板块 | 对应分割条                         |
| ------------------ | -------- | ---------------------------------- |
| `main.nav`         | 主窗口   | 导航左栏与右侧内容区（左右分栏）   |
| `merge.root`       | 整合板块 | 左右两栏（左右分栏）               |
| `merge.left`       | 整合板块 | 左栏内部上下两块（上下分栏）       |
| `merge.right`      | 整合板块 | 右栏内部上下两块（上下分栏）       |
| `guessing.content` | 猜测板块 | 左侧两表与右侧猜测区（左右分栏）   |
| `guessing.left`    | 猜测板块 | 左上对应表与左下别名表（上下分栏） |
| `settings.content` | 设置板块 | 配置类别与配置项（左右分栏）       |

- 位置存引擎 `SplitContainer.SplitOffset` 的**原始值**：以引擎按子节点展开标志 / 最小尺寸（以及拉伸比）算出的默认分隔位置为 0 的像素偏移。读写都原样传递、不做换算，因此恢复效果与用户当时拖拽的结果一致。引擎的默认位置规则：前置节点都不展开 → 默认在容器起点；后置节点都不展开 → 默认在终点；两侧都有展开的节点 → 按拉伸比与最小尺寸取中间。
- 恢复时把偏移与折叠状态设回节点：引擎按当前窗口算出的默认分隔位置 + 记忆偏移共同决定实际位置；当前窗口装不下时由引擎夹紧实际布局、**不写回**记忆值。
- 未知键原样保留（UI 找不到对应节点时忽略），便于版本回滚与新旧版本共存。

### 保存与恢复时机

| 对象         | 记录时机                                                                         | 恢复时机                                                                        |
| ------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 分割条       | 拖拽结束立即触发一次自动保存（拖拽过程中只更新内存，不按帧落盘）；退出时再兜一次 | 面板依赖解析、场景节点就绪后应用一次                                            |
| 主窗口几何   | 关闭窗口时                                                                       | `MainWindow` 初始化时，晚于 `Main.LookGood`，因此不会被「屏幕 75%」的推荐值覆盖 |
| 文件选择窗口 | 关闭时（只记用户真的拖过尺寸的那次）                                             | 弹出时；无记忆值则按视口八成                                                    |

- 窗口移动与缩放事件只更新「普通态矩形」的快照：关闭时若处于最大化，记录的仍是最大化之前的尺寸与位置（同时记最大化标志），下次启动按最大化打开、还原后回到记忆的位置。
- 恢复尺寸时按窗口最小尺寸抬升（记忆值小于最小尺寸时按最小尺寸）；记忆位置若已不在任何屏幕可用区内（如外接屏拔掉），回到主屏可见区居中。

### 设计决策与替代方案

- **独立文件而非并入 `app_settings.json`**：布局是「本机界面状态」，不是用户偏好配置。独立文件让「删一个文件即重置布局」成立，版本过新时的只读保护也只降级这一段，不会连累其它 7 段数据。
- **存 `SplitOffset` 原始值而非比例**：比例要在读写两侧换算、有取整漂移；且默认分隔位置本身随窗口尺寸与子节点展开标志变化，存比例会破坏引擎语义。存原始值零换算、与用户拖拽结果同源。
- **只记真的调过的项**：默认值归场景与 `LookGood` 所有。若连没调过的状态也写进记忆，以后升级默认值（改场景默认、改窗口推荐尺寸）就对老用户永不生效；不写则「回到默认」只需从未调整过或删掉文件。
- **纯拉取、不做 Sync 绑定**：本段是启动 / 弹窗拉取的一次性快照，运行期事实源是节点几何。若按普通配置项挂 `Bind()` 做「模型 → UI」推送，会与用户拖拽 / 缩放互相覆盖；方向只有「UI → 模型 → 落盘」一条（`UiLayoutData` 的类注释同此口径）。

### 加载、迁移与回滚

- 数据版本 `1`（`UiLayoutData.CurrentVersion`）；逐版本迁移留了固定落点，当前只有 v1，无实际迁移动作。
- 版本高于当前程序：**只读**——内存用默认值，本次运行跳过该文件、其余 7 段照常落盘，避免旧版本用自己认识的字段覆盖新格式。
- 字段级容错：窗口宽高非正或越界、坐标越界 → 整个窗口几何回落「未记录」（最大化标志一并复位）；弹窗宽高整对回落；分割条丢空键、重复键保留最后一条、偏移收敛到 `[-100000, 100000]` 像素。
- 坏 JSON：由既有机制备份为 `<文件名>.corrupt-<时间戳>` 后按空数据继续，不静默覆盖现场。
- 回滚：删除 `ui_layout.json` 即重置全部布局；多开实例时后写覆盖先写（不做文件锁——布局丢一次没有数据损失，加锁的复杂度不划算）。

### 测试与验收

- 单测覆盖：模型收敛（非法尺寸与坐标、空键、重复键、偏移越界）、加载 / 保存 / 版本只读保护 / 坏文件备份、窗口几何收敛（小于最小尺寸抬升、离屏回居中）、分割条「有记录则应用、拖拽后落盘、初值未变不新增记录」、文件选择窗口跨重启命中。
- 真机验收口径：拖动分割条 → 退出 → 重启，位置与折叠状态还原（窗口尺寸不同时按「新的默认位置 + 记忆偏移」落位），未拖过的板块保持场景默认；最大化关闭后重启仍最大化，还原后回到关闭前的位置；删除 `ui_layout.json` 后重启回到首次启动的 75% 居中。

## 主题与外观

设置板块「通用」类别页提供界面主题选择：默认（Godot 原生）与 4 套主题，选中即全局生效并随自动保存落盘，重启沿用。本节记录存储契约、运行时机制、度量基线、覆盖范围与设计决策。

### 存储契约

主题只占一个字段：`app_settings.json` 的 `themeId`，默认值 `default`（即「默认（Godot 原生）」）。

- **缺键与旧文件**：反序列化缺键时取构造默认值，`EnsureIntegrity()` 也把显式 `null` 回填成 `default`，因此旧版本写下的配置文件打开即为默认主题；主题不新增存储分段，也不改动数据版本。
- **写入时机**：用户在「通用」页选中即写 `themeId` 并触发既有防抖自动保存；面板只写模型，不自己应用主题。
- **回滚安全**：旧版本程序读到不认识的 `themeId` 只忽略该键，不报错、不丢其它配置，因此从新版本回退到旧版本无需清理配置文件。
- **未知值不全量改写**：界面按默认主题显示并提示，但**不**把 `themeId` 改写成 `default`——该值可能来自手工编辑或其它分支，静默改写等于丢配置。

### 主题清单

清单硬编码在 `ThemeCatalog` 中，顺序即下拉顺序，第一项恒为默认项：

| id              | 显示名             | 资源                                         |
| --------------- | ------------------ | -------------------------------------------- |
| `default`       | 默认（Godot 原生） | 无，不加载资源，界面为引擎默认外观           |
| `dark-default`  | 暗夜（默认）       | `res://src/assets/themes/dark-default.tres`  |
| `light-default` | 浅色（默认）       | `res://src/assets/themes/light-default.tres` |
| `indigo-night`  | 靛蓝夜色           | `res://src/assets/themes/indigo-night.tres`  |
| `high-contrast` | 高对比             | `res://src/assets/themes/high-contrast.tres` |

`id` 是持久化契约的一部分，改名等于让用户丢掉已选主题，必须保持稳定；显示名可以改。`light-default` 另带「浅色」标记，用于换浅色版 Logo。

### 运行时机制

- **应用点是根窗口**：切换主题改的是主窗口的 `Window.Theme`，不是项目设置。4.7.1 的 `ThemeDB` 没有运行时设置项目主题的入口，`gui/theme/custom` 只在启动时读取一次，改它不会在本次运行生效；根窗口的 `Theme` 沿节点树向下查找，是运行时唯一可靠的全局入口。
- **窗口底色单列**：改 `Theme` 不会改窗口清屏色，故窗口底色放进主题的自定义类型 `AppColors` 的 `window_background`，由应用器在应用主题的同时改写 `RenderingServer` 的默认清屏色。默认主题或主题缺该色时回退到**启动时捕获**的引擎清屏色——应用主题后清屏色已被改写，晚取就拿不到原值。
- **顺序**：启动时先加载数据、应用存档主题，再还原窗口几何。主题只改配色不改尺寸，先定外观再摆几何可避免按旧外观露出第一帧；退出时先立退出护栏，已排队的应用被守卫挡掉。
- **失败一律回退默认**：未知 id、资源路径不存在、加载抛异常、资源不是 `Theme`，全部回到「无主题加默认底色」并记录原因，绝不留半套主题。
- **面板只写模型**：设置页只写 `Settings.ThemeId`，实际应用统一由 `MainWindow` 订阅该值的 Sync 绑定完成，回调只 `CallDeferred`，绑定在 `_ExitTree` 释放。这样主题切换与窗口几何还原、WebSocket 重启共用同一套生命周期护栏；面板自己下发应用会绕开启动顺序与退出守卫。
- **语义色读取**：日志正文、录制状态、GIF 副标题、WebSocket 状态等原本硬编码的颜色统一经 `AppPalette` 从主题链取 `AppColors` 下的颜色，取不到时回退默认主题的原常量，保证「默认」观感与接入主题前完全一致。
- **面板重画时机**：已渲染进控件的颜色（日志的 BBCode、状态行的 `font_color` 覆盖）在写入时就固化，主题变化不会自动更新，日志 / 录制状态 / WebSocket 状态面板订阅 `ThemeChanged` 后只 `CallDeferred` 一次重算（同帧多次通知合并）。**不能在 `theme_changed` 回调里同步重算**：主题通知是父→子，父控件自己的回调触发时它和子控件解析主题项拿到的仍是上一套值，会把旧主题色固化下来（浅色 accent 落到深底上呈近黑）。日志面板整段重建还会与待处理队列去重：先快照缓冲区，再排空待处理队列，最后只补画不在快照里的条目（按引用判同一条目），否则同一批条目会被 `_Process` 再画一遍，表现为同一毫秒的重复行。已知行为：补画条目追加在快照条目之后，单帧积压超过缓冲区容量时，被挤出缓冲区的旧条目会排在最新行之后，短时间内顺序与时间戳不一致（不丢行）；正常缓冲容量（1000）下不会触发。

### 度量基线

主题按 `gui/theme/default_theme_scale = 2.0` 的实测尺寸设计，下表为 `StyleBoxFlat` 的内边距与圆角（单位 UI 像素）：

| 控件             | 内边距（左右 / 上下）                                              | 圆角 |
| ---------------- | ------------------------------------------------------------------ | ---- |
| Button           | 8 / 8                                                              | 6    |
| LineEdit         | 8 / 8                                                              | 6    |
| OptionButton     | 16 / 8                                                             | 6    |
| Tree             | 8 / 8（下 10）                                                     | 6    |
| PopupMenu        | 8 / 8                                                              | 6    |
| Tooltip          | 16 / 4                                                             | 4    |
| ProgressBar      | 4 / 4                                                              | 12   |
| Window           | 20 / 上 56、下 16；`embedded_border` 外扩 = 左/右 16、上 64、下 12 | 6    |
| ScrollBar 抓握块 | 8 / 8                                                              | 20   |

- 只改颜色、边框与圆角，**不覆盖字体与字号**：字号决定行高与控件最小尺寸，一旦覆盖会让表格行高、按钮与输入框高度整体漂移，出现「换个主题布局就变」。保持字体链不变，主题之间只有配色差异。
- 新增或调整主题时，度量必须与上表一致；不确定就照抄现有 `.tres` 里的同名 `StyleBoxFlat`，不要凭观感改数值。
- **Window 的 `expand_margin_top` 是标题栏能否着色的关键**：Godot 的 `Window` 没有独立标题栏样式，标题栏背景只能由 `Window/styles/embedded_border`（失焦用 `embedded_unfocused_border`）的 `expand_margin_*` 向外扩展覆盖。`scale=2.0` 下标题栏高 `title_height=72`，故 `expand_margin_top` 必须为 64（与引擎默认一致），否则标题栏上方 56px 没有背景、内建窗口标题文字悬浮在透空区（`.tres` 一旦覆盖该 StyleBox 就是整体替换，expand 不会与默认值合并）；只改 `title_height` 无效。改 `gui/theme/default_theme_scale` 时需按比例同步这组数值。

### 覆盖范围

一套主题覆盖下列类型，缺项会退回引擎默认样式、在深色底下表现为突兀的浅色块：

| 分组       | 覆盖内容                                                                         |
| ---------- | -------------------------------------------------------------------------------- |
| 容器与弹窗 | Panel、PanelContainer、PopupPanel、PopupDialog、AcceptDialog                     |
| 文本       | Label、RichTextLabel                                                             |
| 按钮       | Button、OptionButton、CheckBox                                                   |
| 输入       | LineEdit、TextEdit、SpinBox                                                      |
| 列表       | ItemList、Tree、PopupMenu                                                        |
| 滚动与分隔 | HScrollBar、VScrollBar、HSeparator、VSeparator、HSplitContainer、VSplitContainer |
| 进度       | ProgressBar                                                                      |
| 窗口与提示 | Window、TooltipPanel、TooltipLabel                                               |
| 语义色     | `AppColors` 的 7 色                                                              |

`AppColors` 是不对应任何控件的自定义类型，只作 `Theme.SetColor` 的类型容器，含 7 个颜色：`window_background`、`status_ok`、`status_warn`、`status_error`、`muted_text`、`accent`、`log_text`。默认主题没有资源文件，由代码里的兜底常量提供同样 7 个值。

### 浅色主题的图标与 Logo

深色底上的图标多为浅色描边，放到浅色主题下几乎看不见，故浅色主题额外替换 13 个图标：Tree 箭头与勾选 6 个、分割条抓握 2 个、窗口关闭 2 个、OptionButton 箭头 1 个、文件对话框缩略图 2 个。其中 12 个由引擎默认图标逐像素 RGB 反相得到；`Tree/icons/unchecked` 是引擎里唯一的深色半透明图标，反相会变成浅灰块、在浅底上反而不可见，故该图不做反相、按原图导出（浅色底上呈深灰块，语义与默认主题一致）。图标放在 `src/assets/themes/icons/dark/`，由主题以 `Texture2D` 外链引用；PNG 走 LFS。目录名里的 `dark` 指图标本身是深色（供浅色主题用），另外三套深色主题不引用这些图标。

- **FileDialog 的 6 个 `menu_*` 图标不覆盖**：它们在引擎运行时主题里是空纹理，主题即便声明也拿不到可显示的内容，写了等于无效条目，右键菜单沿用引擎绘制。
- **左上 Logo 随明暗切换**：浅色主题换 `logo-lockup-light.svg`，其余主题用 `logo-lockup.svg`。切换按**实际生效**的主题判定，未知 id 或加载失败回退默认后自然落回深色版；贴图缺失时保持场景里的原值，不清空。
- **CheckBox/CheckButton 的勾选图标不覆盖**：引擎默认主题里这两个控件的图标本身就是实心方块（未勾选为填充块、勾选在填充块上叠加勾痕），浅色主题只能靠 `checkbox_*_color` 做乘法调色，因此未勾选态呈深色实心方块；这是引擎图标形状而非本次引入，未额外手绘图标，验收时按此观感确认。

### 设计决策与替代方案

- **固定清单而非目录扫描**：清单就是界面契约——下拉顺序、显示名、哪个主题算浅色都由它决定。目录扫描会把「多加一个 `.tres`」变成「界面上悄悄多一项」，显示名与明暗标记还得另找来源；固定清单强制新增主题走一次显式注册，代价只是多改一处。
- **根窗口主题而非项目设置**：项目设置只在启动读取（见「运行时机制」），改它要重启，达不到「选中即生效」；根窗口 `Theme` 是运行时唯一可靠的全局入口。代价是主题不写进导出预设，随应用资源一起分发。
- **文本 `.tres` 而非主题工具生成**：主题内容全是 `StyleBoxFlat` 与颜色，文本资源可读、可 diff、可手改数值，评审时能直接核对度量是否守基线；MCP 的主题工具没有 `StyleBox` 能力，走它反而要二次编辑。规则 13 只约束 `.tscn`，`.tres` 以文本提交不记例外。
- **`AppColors` 自定义类型而非硬编码**：窗口底色与四个状态色没有对应控件，散落在各面板里硬编码就跟不上主题。收进主题的自定义类型后读取统一经 `AppPalette`，默认主题再给同一组兜底常量，既让浅色主题可用，又保住默认观感不变。
- **分割条背景透明**：`HSplitContainer`/`VSplitContainer` 的 `split_bar_background` 用全透明 `StyleBoxFlat`，让分割条区域直接透出窗口底色；若用半透明强调色会形成一条与窗口/面板都不同的色带（真机反馈的「Split 颜色和底色不一样」即此）。可拖拽提示由抓握点图标承担，不靠底色区分。
- **发布出的表格图片不受主题影响**：两张表的图片配色是固定调色板而非主题色，主题切换不会改变群里收到的表；表格只借主题链取字体与字号，而主题不覆盖字体，故出图尺寸与观感也稳定。

### 新增主题的维护步骤

1. 复制一套现有 `.tres` 改颜色，控件清单与度量基线与原文件保持一致（缺项会退回引擎样式，改数值会造成布局漂移）。
2. 在 `ThemeCatalog` 的清单里按期望顺序注册 `id`、显示名、是否浅色与资源路径；只有浅色系主题才标记浅色。
3. 跑 `ThemeCatalogTest`：用例会校验清单契约（5 项、首项为默认、id 唯一）、资源可加载、7 个语义色齐全、条目必须是引擎默认主题里的同名同类型条目、必备控件条目存在、未覆盖字体与字号，以及浅色主题的 13 个图标映射。拼错的条目会在这里失败，而不是在界面上静默失效。

## 符卡 GIF 录制模块

由 CMEX 驱动 LuaSTG 引擎进程，自动逐张录制 Boss 的符卡与非符，产出与手工整理**同构**的 GIF 集（`manifest.json` + `序号.gif`），以复用信息板块既有的导入与展示链路。

### 引擎侧启动契约

启动参数是一个**单参数**，内容是 Lua 赋值代码（整串用双引号包裹，值内不得出现引号或换行）：

```
LuaSTGSub.exe "setting.mod='<工程包名>'; setting.autocmex_job='autocmex/jobs/<任务号>.json'; setting.showcfg=false; start_game=true; cheat=true"
```

- `start_game=true` 必带，否则引擎会把 `setting.mod` 覆盖成启动器。
- `cheat=true` 必带：`cheat` 是引擎全局无敌开关，不开则自机被弹幕撞死、卡提前结束、GIF 不完整。
- **不覆盖** `setting.resx/resy`：分辨率归玩家 `userdata/setting.json` 所有，覆盖会改坏画面比例；GIF 尺寸因此随玩家设置浮动（实测玩家 1280×960 且录制器 `scale=0.5` 时产物为 640×480）。
- `setting.autocmex_job` 这类裸赋值自定义键不会被引擎写回 `userdata/setting.json`，故插件可常驻 `game/plugins/autocmex/` 且不影响玩家正常启动。

### 任务与结果契约

任务由 CMEX 写、结果与诊断日志由插件写，目录固定为 `<引擎>/game/autocmex/{jobs,results,logs}/`（由 CMEX 预建）；任务内的路径一律用正斜杠、相对 `game/`（即引擎进程的工作目录）。

| 阶段 | `phase`     | 任务关键字段                                                               | 结果关键字段                                                                               |
| ---- | ----------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 枚举 | `enumerate` | —                                                                          | `boss_name` / `boss_class` / `cards[]`（`absolute_index`/`name`/`is_sc`/`is_combat`/`t3`） |
| 录制 | `record`    | `absolute_index` / `interval` / `max_frame` / `scale` / `include_previous` | `task_name` / `gif_path` / `frames` / `complete` / `success` / `size`                      |

- 结果必须回传同一 `job_id`，CMEX 据此拒绝上一轮遗留的结果文件。
- 插件先写 `.tmp` 再改名，避免 CMEX 读到写了一半的 JSON。

### 关键设计决策

- **跳卡置 `lstg.var.sc_index = nil`**（而非沿用 `StageDebugView` 的 `-1`）：`UI.lua` 只判真值就直接索引 `_sc_table[sc_index][1]`，`-1` 会索引 nil 崩渲染。
- **逐帧推进靠包装全局 `DoFrame`**：引擎每帧按名字取该函数；插件在 `afterTHlib` 事件后包装，并在原函数执行**完毕之后**判定当前卡（`b.current_card` 由 `DoFrame` 内部赋值）。
- **收尾以录制器自报为准**：`get_last_record_info()` 的 `success`/`frame`/`task_name`/`size` 可直接读，无需轮询文件大小；录满 `max_frame` 时由录制器自行收尾，插件不得重复 `end_record`。
- **产物分辨率由放缩比决定**：插件在 `start_record` 之前调录制器的 `set_scale(job.scale)`，产物像素 = 捕获区域 × `screen.scale` × 放缩比（与录制器 `CreateRenderTarget` 的算法一致，故日志里会打出预期尺寸）；与抓帧区域同理，`set_scale` 也只在 `status == "initialized"` 时生效。CMEX 侧以整数百分比暴露（`ScalePercent`，10..100，默认 50 = 录制器默认的 0.5），写任务文件时除以 100 还原成倍率；插件只做「正数 + 0.1..1.0」的兜底收敛（越界会写 `WARN`）。放缩比同时影响清晰度与产物体积，故它是 30MB 换挡判据的上游变量。
- **同一引擎目录不可并发**：录制器产物名是秒级时间戳、临时目录在启动时被清空，并发会互相破坏，串行化由编排层保证。
- **进程超时必须把编码耗时算进去**：`end_record` 同步编码，实测约 0.08–0.17 s/帧（350 帧约 36 s、702 帧约 58 s）。
- **卡表口径**：`_editor_class[boss].cards` 含对话阶段，`_sc_table` 只含符卡，二者不同构；序号一律取 `cards` 中的**绝对下标**（1 基）。字段与引擎自身判定同源：`is_combat` 由 `spboss.lua:1433`（`c.is_combat = not (fake)`，对话卡按 `fake` 处理后为 `false`）置位，`is_sc` 由 `boss_card.lua:44`（`c.is_sc = (name ~= '')`）置位；`t3` 在引擎内是**帧**（`boss_card.lua:42` 的 `int(t3) * 60`），插件按 ÷60 换算成秒后写出。

### 单卡录制闭环（P2）

`RecordingOrchestrator.RecordCardAsync(engineDir, modPackName, card, config, cancellationToken, timeout, onAttemptStarted)` 把一张卡录成录制器产物（单卡只录不归集）；`{序号}.gif` 的命名与序号在 `RunAsync` 归集时统一重写，与录制器自报的秒级时间戳产物名解耦。

- **「录两遍」是常态而非补救**：`config.MaxFrame` 默认 350 帧，`interval=3`（20 fps）只覆盖 17.5 秒，长卡必然录满被截断；故首次 `result.complete == true`**或首次产物已达 QQ 的动图体积上限**（`GifSizeLimitBytes` = **30,000,000 字节**，即 30MB 按十进制取——这是两种可能口径里**保守**的那个：若 QQ 实际按 1024 进制限流，十进制阈值只会更早触发换挡、不会漏放；反之取 1024 进制则会放过 30,000,000..31,457,280 字节这一段，而真机上确有一张 30,291,854 字节的产物落在该带内）即换 `config.SecondInterval`（默认 5，12 fps）重录一次，并**采用第二次的产物**，`RecordingCardOutcome.Attempts` 记为 2。两条触发条件共用同一段重录逻辑（判据集中在 `DescribeSecondAttempt`）：截断的日志沿用「录满 N 帧被截断」，体积的日志给「产物 X MiB 已达 30MB 上限」；重录失败的原因按触发条件区分为「首次截断后重录失败」与「首次产物超限后重录失败」。换挡后仍 `>= 30MB` 时**不做第三次尝试**：产物本身可用，故照常采用，只补一条带卡号与体积的 `WARN` 日志供真机定位；每张卡收尾时也会把产物实际体积（MiB，与资源管理器显示同口径）打进日志。
- **截断即视为不完整**：凡触发重录的卡（含体积超限触发的换挡）一律回 `Complete = false`（保守口径），实际帧数与间隔照实回传，由调用方决定是否接受。
- **失败重试只发生在单次尝试内部**：超时 / 非零退出 / 结果缺失 / 产物缺失 / 卡名核对不符即自动重试 1 次；两次都失败则本卡判失败并返回原因。第二次尝试彻底失败时**不**回退首次的截断产物——半截 GIF 混进集里比明确失败更难排查。
- **单次尝试的超时预算**：`min(card.t3, maxFrame × interval ÷ 60) + 45 秒启动余量 + maxFrame × 0.3 秒编码余量`（`CardTimeout`）；预算按「一次尝试」计，不随重试与第二次尝试叠加。
- **归集**：`GifSetBuilder` 负责把录制器产物按 `{CombatOrdinal}.gif` 拷进输出目录（同名覆盖），并读 GIF 逻辑屏尺寸回填 `Width`/`Height`；产物无 GIF 魔数或头截断时抛 `InvalidDataException`，由编排层转成可展示的失败原因。

真机验收（2026-09-25，`sample_pre_project`）：枚举 8 张卡（4 对话 + 2 非符 + 2 符卡），取 `t3` 最短的「耐久符」（绝对下标 8 → 序号 4）→ 首次 `interval=3` 录满被截断 → 自动 `interval=5` 重录 → 采用第二次产物 `274 帧 / 12 fps / complete=false`，输出目录仅 `4.gif`（640×480），2 次尝试 = 2 次进程启动。

### 批量并行录制（P3）

一轮的入口是 `RecordingOrchestrator.RunAsync(request, progress?, token)`：清扫残留沙箱 → 前置检查 → 枚举 → 并行逐卡录制 → 串行归集 → 写报告 → 删沙箱。

**沙箱隔离**（`RecordingSandbox`）：真引擎目录全程只读——每轮把工程包与运行必需的引擎文件复制进 `<沙箱根>/sb_<yyyyMMdd_HHmmss_fff>_<4位随机>_w<worker 序号>/` 的独立副本，任务、结果、`engine.log` 与录制器产物全落在沙箱里，归集时才往输出目录写。原因是录制器把 `danmaku_recorder/tmp` 当进程级工作区（`recorder:init()` 会清空它）、产物名又是秒级时间戳，多实例共用同一引擎目录必然互相破坏。沙箱清单只含运行必需项：`packages/`、`plugins/`（含 `autocmex` 与弹幕录制器插件）、`userdata/`、启动文件与 `*.dll`；`mod/` 只放本轮手选的工程包。

- 沙箱根默认取系统临时目录下的固定子目录，可由 `config.SandboxRoot` 覆盖。
- 每轮开始清扫**超 1 小时**的 `sb_*` 残留（上次崩溃留下的）；建沙箱前按「引擎 + 工程包 + exe」估算单份占用，剩余空间不足直接中止（不半途失败）。

**并行调度**（`RecordingScheduler`）：worker 数 = `min(config.Parallelism（默认 16，上限 32）, 战斗卡数)`，再按临时卷剩余空间压一次（只降不报错，被压过则回一条 `Warning`）。枚举用的那个沙箱直接复用给 worker 1，省一份复制；其余 worker 各自建沙箱。取卡是「抢」的——谁先空出谁取下张，逐卡结果按 `combatOrdinal` 回填，故报告顺序与「谁先录完」无关。

- 单卡失败只记该卡，不中断整轮。
- **取消**：停止领卡并杀掉在跑的进程树；随后照常归集已产出、删沙箱、写报告，正在录与没轮到的卡一律记「未录制」，报告 `cancelled = true`。预取消（进轮前就已取消）连沙箱都不建。

**归集与报告**（固定串行）：输出目录与报告是全局共享资源，且报告必须按战斗序号升序，故归集不并行——逐卡 `GifSetBuilder.PlaceCardGif` 改名落地（`{序号}.gif`，同名覆盖）、读 GIF 头回填宽高，再按卡表顺序组装 `RecordingCardReport`（帧数 / 帧率 / 时长 / 完整标记 / 尝试次数 / 进程启动次数 / worker / 失败原因 + `engine.log` 尾部）。「拿到结果的才判成败，没轮到的一律记未录制」，据此可区分「试过没成」与「压根没轮到」。

- **报告**：`RecordingReport` 落 `<输出目录>/recording_report.json`；写盘失败只作为 `Warning` 回传，不把整轮判失败。
- **进度**：`IProgress<RecordingProgress>` 按「阶段（枚举 / 录制 / 归集）+ 总数 + 已完成 + 已失败 + 各 worker 正在录的卡」发快照，内部加锁聚合。
- **返回值**：`RecordingRunResult` 含 `Error`（前置失败原因）、`Report`、`OutputDir`、`ManifestPath`（本轮清单路径；`null` = 无可导入内容）、`Warning`（并行度被压缩等非致命提示）与 `EngineLogTail`（前置失败时附）。

真机验收（2026-09-25，`sample_pre_project`，4 张战斗卡）：2 worker 并行跑通全流程——沙箱各自独立、产物按序号归集 4 个、报告落盘、临时目录无残留沙箱；`t3` 封顶的「耐久符」与串行轮的产物帧数/帧率一致（274 帧 / 12 fps，抽样比对内容近似度 84~85%）。按既定裁定「截断属正常产物」：玩家不干预时 45~60 秒的长卡在 350 帧预算下两档都会截断并标 `complete = false`。

### 配置与插件部署（P4）

设置板块「信息」类别页在目标群列表下方挂一组常显的「符卡 GIF 录制设置」（`RecordingConfigPanel`，已取消折叠复选框）：引擎目录、并行度、沙箱根、插件状态、高级参数五段。该类别页没有独立场景（节点直接写在 `SettingsPanel.tscn` 里），故分组由 `InfoConfigPanel` 在依赖解析后按需 `GD.Load<PackedScene>("res://src/ui/settings/RecordingConfigPanel.tscn").Instantiate<RecordingConfigPanel>()`（与 `AiModelConfigPanel` 加载 `ModelEntryPanel.tscn` 同范式），`Name` 设为 "RecordingSection"，挂到页面内容的 `%PageBody` 末尾，并在该页每次被切显时刷新一次状态（`VisibilityChanged`）。结构与静态文案都在独立场景里（规则 7/8/13 已满足），代码只做 `[Node]` 注入、信号连接、运行期才能算出的文本（默认沙箱占位符、常量上限 tooltip）与 Sync 绑定。

`RecordingConfigPanel` 按规则 1/5 接入 AutoInject：`[Meta(typeof(IAutoNode))]` + `_Notification` 转发给 `this.Notify`，DataManager 走 `[Dependency]`（由设置面板树内的 provider 就近提供）；控件结构全部来自 `RecordingConfigPanel.tscn`，代码在 `OnReady` 只连接信号与运行期文本，配置回填与 Sync 绑定在 `OnResolved` 装配（依赖重新解析时先释放旧绑定，规则 20）。**按需创建的理由**：本页没有独立场景，分组随页面打开才需要实例化，故不在 `SettingsPanel.tscn` 里常驻。

**双滚动结构是有意设计**：目标群列表行数随活动规模浮动，固定高度（600px）单独滚动可避免把页面撑长；录制设置整组较长，放在列表下方由页面滚动承接。

替代方案与取舍：① 只做一层滚动（群列表随页面滚）——群列表会把录制设置顶远，行数一多页面极长；② 列表高度按内容自适应——行数变化会让页面高度跳动、滚动位置不稳定；故取固定 600px。

**滚轮边界交接**：Godot 4.7 的 ScrollContainer 只在自身滚动值真的变化时才消费（accept）滚轮，到边界后事件会自然冒泡给父级容器——「列表到底继续滚页面」由引擎默认提供，本页不写额外代码（内层还有余量时滚列表、到边界后滚页面、列表装得下时直接滚页面）。

配置项一律复用 `DataManager.RecordingConfig` 的既有字段（引擎目录 / 并行度 / 沙箱根 / 帧数上限 / 两个抽帧间隔 / 放缩比 / 上次输出目录），写入走既有防抖自动保存。写回纪律：

- **非法值不落盘**：引擎目录经 `EngineLocator.TryValidate`、沙箱根经 `RecordingSandbox.TryValidateRoot` 校验，不通过则保留原值、只把原因写在状态行上——提示与配置分离，避免「面板提示已改、实际没改」的错觉。
- **越界收敛**：并行度 1~32、帧数上限 1~1000、抽帧间隔 1~60、放缩比 10~100（步进 5，百分比），由 `RecordingConfig.ClampParallelism`/`ClampMaxFrame`/`ClampInterval`/`ClampScalePercent` 收敛后写回。
- **推断只作建议**：「从 Sharp 目录推断」复用 `EngineLocator.TryInferFromSharpDir`（沿「整合」板块的 Editor Sharp 目录上溯找 `game/launch`），结果仍走同一套校验，不隐式改写用户配置。

**插件部署**（`PluginDeployer`）：判定与动作收在一处，UI 与沙箱共用同一判据（`TryValidateForRecording`），避免出现「面板显示就绪、起录却被拒」的两套口径；`RecordingSandbox.ValidateSource` 不再自己判插件，只转述该判据的原因串（原异常文案逐字不变）。

- 三态：`Ready`（目录在且启用）、`InstalledDisabled`（目录在、清单 `enable = false` 或清单缺失导致引擎不会加载）、`Missing`；清单文件存在但不可解析时另给 `ManifestBroken`，此时**一切部署动作关闭**——宁可不让用户动手，也不拿坏清单去写。
- **清单缺失不等于损坏**：文件不存在时按空清单继续判插件（`ManifestExists = false`），安装动作会把清单新建出来，故在全新引擎上不会出现「两个按钮全灰、用户无从下手」。判据只有一处差别：录制前的 `TryValidateForRecording` 把「清单缺失」直接判为不可录（引擎不读清单就等于不加载插件），能装 ≠ 能录。
- 条目命中比的是**整段目录名**（先 `name` 精确匹配，再比 `path` 的最后一段；第三方插件允许版本后缀，并剥掉 `[pluginpackage]` 前缀），不按子串匹配——否则 `autocmex_old` 这类同名前缀目录会被误当成目标条目，安装会去改写别人的 `enable` 而不是新增一条。
- 清单兼容两种登记方式（新式 `name` + `path` 与 LuaSTG-CN 的 `[pluginpackage]danmaku_recorder_x.y.z` 路径）。引擎目录未设置、清单损坏、缺第三方录制器三种情况各自给可执行的原因（缺录制器明说「第三方插件，需自行获取」）。
- **一键安装**（自家插件）：先备份既有插件目录（`<目录名>.autocmex-bak`，已存在则不叠加）→ 复制自带插件 → 登记为启用；**幂等**，重复点击不产生第二份备份、不重复登记。清单损坏时抛 `PluginDeployException` 且不改盘。
- **一键启用**（第三方弹幕录制器）：只把条目 `enable` 置 `true`，不动文件、不覆盖条目里的其它字段。
- **写前必备份**：改 `plugins.json` 前先落 `plugins.json.autocmex-bak`，再以临时文件 + 原子替换写入，避免半截 JSON 让引擎读不到任何插件。
- **零写入约束**：用户没点任何按钮时，面板只做只读检查（`Inspect`），不碰引擎目录。
- 沙箱侧新增 `TryValidateRoot`（沙箱根存在性 + 一次性写入探针；配置为空时允许就地创建默认目录，用户手选的目录必须已存在）；`EstimateFootprint` 允许工程包路径为空（设置页刚配引擎时还没有包），缺失项按 0 计。

验证（当时）：编译 0 错误，GoDotTest **588 通过 / 0 失败**（带窗口运行；新增 `PluginDeployerTest`（三态判定、清单损坏、清单缺失、同名前缀目录不误命中、禁用条目、只读检查不写盘、安装幂等与备份、启用最小改动、缺件原因串逐字比对）、`RecordingConfigPanelTest`（配置回填、非法值不落盘、越界收敛、推断失败不写配置、状态渲染与按钮启停、一键部署联动与失败原因、无引擎目录时误点不改盘）与 `RecordingSandboxTest` 的 `TryValidateRoot` 与四种插件缺件拒绝建副本）。

### 录制入口、`manifest.json` 与自动导入（P5，已完成）

入口复用信息板块 GIF 集栏里既有的「录制」按钮（`GifSetPanel.%RecordButton`，此前为占位禁用），不新增类别页；录制相关的导入对话框与进度对话框改由 `GifSetPanel.tscn` 承载。点击后按序执行：**前置检查**（引擎目录、插件状态、沙箱根，复用 `PluginDeployer` 与 `RecordingSandbox.TryValidateRoot`；不通过则不起任何进程并在原处说明原因）→ **手选工程包 zip** → **手选输出目录** → `RecordingOrchestrator.RunAsync`；进度以模态对话框 `RecordingRunPanel` 呈现。该对话框是 `RecordingRunPanel.tscn` 的场景实例，以 `%RecordingRunPanel` 内嵌在 `GifSetPanel.tscn` 里；对话框脚本用 `[Node]` 注入四个 Label（阶段 / 完成计数 / 各 worker 正在录的卡 / 结束汇总）。`RecordingRunner` 不再是构造参数，而是 `IRecordingRunPanel` 接口上的 `Runner` 属性（命令而非服务，单测替换它以驱动对话框）；`Start` 在 `Runner` 未装配时抛 `InvalidOperationException`。取消按钮仍由 `AcceptDialog.AddButton` 创建——对话框自带 chrome 的文档化例外；取消语义沿用既有：关闭窗口即取消本轮，已归集的产物与报告保留。

`manifest.json` 由编排层在**归集之后**写出（只有归集后才拿得到尺寸），字段来源：

| 字段                                      | 来源                                                   |
| ----------------------------------------- | ------------------------------------------------------ |
| `setName`                                 | 手选工程包文件名（去扩展名），即报告里的 `ModPackName` |
| `bossLabel`                               | 游戏侧 Boss 名，枚举时一并 dump（报告里的 `BossName`） |
| `generatedAt`                             | 本轮开始时间，`yyyy-MM-dd HH:mm:ss`                    |
| `entries[].index` / `spellCardName`       | 战斗序号（1 基，只数符卡与非符）/ 卡名                 |
| `entries[].fileName` / `width` / `height` | `{序号}.gif` 与归集时读到的 GIF 头尺寸                 |

写盘**显式使用 camelCase**（`GifSetManifest` 的属性是 PascalCase，读侧大小写不敏感，但契约与文档示例是 camelCase）。**只收 `status == ok` 的卡，序号允许有洞**（集内校验只要求序号为正且唯一）；**0 张成功则不写清单、不导入**。

导入与选中由 UI 层调用方完成，`core/recording` **不反向依赖** `core/info`：`GifSetService.ImportFolder(输出目录)` 成功后**显式**调 `SetActiveSet`（`Register` 只在「当前集为空/失效」时才自动选中），并回写 `RecordingConfig.LastOutputDir`。

失败落点：前置检查不通过 → 不起进程；**导入被拒** → 产物、报告、清单全部保留，逐行列出导入结果明细并提示可手动导入；**输出目录含本轮未声明的 `.gif`** → 不删用户文件、跳过导入并列出明细（集内校验要求清单与目录内图片一一对应，上一轮残留的 `.gif` 会让导入被整体拒绝）。截断（`complete = false`）仍按既有裁定视为正常产物。

## 信息板块

### 目标群入口收敛到设置页

- **决策**：目标群的增删、改名、启停与「从 Koishi 刷新群列表」全部只在设置板块「信息」类别页；信息页不再提供目标群勾选条，发布目标 = 设置页里「启用」的目标群；「一键转发」与「猜测表变化自动推送」移到信息页顶部操作行。
- **依据**：目标群本质是配置而不是版面内容；原先两处勾选共享同一个 `Enabled` 标记，维护入口分裂会让用户在两页之间来回确认。收敛后「发布目标」可直接由设置页状态推导，信息页只保留发布动作；「刷新群列表」也必须留在维护目标群的那一页。
- **替代方案**：保留底部勾选条、把设置页启用开关改为只读（否定：刷新群列表仍需设置页，两处仍要跳转）；或在信息页提供只读群列表（否定：占版面且无操作价值）。
- **代价**：信息页不再一眼看到「这次会发到哪些群」，需要切到设置页核对；发布时若未启用任何群，提示会引导用户去设置页启用。

### GIF 集展示的懒加载决策

- **驻留判据**：卡片矩形与滚动视口有交集（哪怕只露出 1 像素）即驻留解码，滑出视口立即释放帧缓存；**不设「同屏最多 N 张」上限**。
- **为什么取消上限**：按内容顺序截断会把「完全可见但排在后面」的卡片丢掉，表现为 GIF 空白、滚动后才出现；而视口能同时容纳的卡片数天然有限，内存上界即「视口高度 ÷ 卡片高度」，额外上限没有收益。
- **刷新时机**：滚动、滚动视口与卡片列表尺寸变化（窗口缩放/最大化、拖拽分栏）、面板显隐、重建卡片都会触发重算；同一轮布局事件合并为一次调度，首轮回调后再兜一次刷新，按容器排序落定后的几何复核（不写死具体帧数——容器排序与 deferred 回调的先后由引擎决定）；同路径已加载或解码在途的卡不会因复核被重启解码。
- **后续**：若引入视口外的预加载区，上限只约束预加载部分，不得挤占视口内的卡片。

### 表格图片拖拽与复制

- **决策**：两张表的预览支持右键「复制」与按住拖拽导出，产物与「发布」同源；实现走仓库自带的 Windows 原生封装（OLE 拖放 + 剪贴板），不引入第三方库、不新增 NuGet。
- **引擎缺口**：Godot 4.7.1 没有"把内容拖出窗口"和"图片写剪贴板"的 API（`Window` 无 `drag_files`，`DisplayServer` 只有读图）；上游相关提案/PR 长期未合入，第三方仅 Linux X11 实验实现，因此 Windows 侧自写封装是当前唯一可靠路径。
- **实现要点**：`TableImageRenderer` 增加内存出图入口（PNG 入口复用同一渲染）；`TablePreviewExport` 缓存当前表格图片并提供右键菜单与拖动阈值判定；`Win32ClipboardImage` 写 `CF_DIB` + 注册格式 `PNG`；`Win32DragOut` 用 OLE `DoDragDrop`，数据对象同时提供 `CF_HDROP`/`CF_DIB`/`PNG`，拖影经 `IDragSourceHelper` 设置。拖放光标（小方框、绿色加号、🚫）交给系统默认反馈。
- **替代方案**：等上游引擎合入（时间不可控）；引入第三方 GDExtension（Windows 无可用实现）；改用外部命令写剪贴板（慢且无法模拟拖拽）；只做「另存为」（不满足拖拽导出诉求）。
- **代价与已知行为**：仅 Windows；`DoDragDrop` 同步阻塞主线程（拖拽期间界面暂停刷新，松手恢复）；拖拽/复制使用系统临时目录里的唯一命名 PNG，不主动删除；非 Windows 不提供这两个入口。
- **测试**：出图/指纹/组件（Fake 后端）单测、Windows 剪贴板往返单测、面板接线测试；真实拖拽需真机验收（拖到资源管理器/聊天软件、目标拒绝显示 🚫、粘贴复制图）。

### 管线（Sharp 成功后 zip 后处理）

- 触发：Sharp Cli 成功产出 `<输出目录>/<输出名>.zip` 后执行；未配置 Sharp 或打包失败时不产生 mod zip，只在冲突/日志列表说明「未生成 mod zip，混淆未生效」。
- `.lua` 条目：开启混淆时逐条替换为混淆后的 Lua 5.1 源码，条目名与相对路径不变；关闭时原样复制。
- `<输出名>.lstgproj` 条目：**只看「导出包含 `.lstges` 工程文件」**——开启保留、关闭移除，混淆开关不参与判断；混淆关闭但工程文件开关关闭时，仍执行「移除工程文件」这一步。
- 其余条目：按字节原样复制，保留条目 `FullName`（含反斜杠）、外部属性与顺序；zip 在内存中逐条目重建并重写，不解压到磁盘再压缩（后者会规范化条目名并改变顺序）。
- 混淆关闭且工程文件保留：不做任何后处理（保持既有导出行为）。

### 运行期

- 从 `res://src/tools/lua-obfuscator/` 读清单并逐文件校验 SHA256（编辑器运行与导出后的 PCK 都经 Godot 文件接口读取）；校验通过后释放到 `%TEMP%/AutoCMEX/tools/<bundleHash>/`，已存在且逐文件校验通过则复用；不联网下载任何内容。
- 完整性锚定：`bundleHash` 由代码内 `ExpectedBundleHash` 锚定——按清单重算值、清单声明值、代码锚三者必须一致，任一不符即 fail-closed（工具文件被修改或版本漂移）；升级或替换任一运行期工具文件需同时更新 `manifest.json` 与 `ExpectedBundleHash`（README 等非运行期文档不参与哈希，改它不影响锚值）。
- 以绝对路径子进程调用：`lua5.1.exe <cli.lua> --config <cfg> --Lua51 --nocolors --out <out> <in>`；不显示窗口、重定向 stdout/stderr；Prometheus 不支持批处理，故一个 `.lua` 一个进程。
- 超时：单文件混淆 180 秒、输出加载校验 60 秒，超时杀进程树并判该文件失败。
- 预处理与校验：混淆前去除 UTF-8 BOM（Prometheus 对 BOM 报词法错误）；输出须非空、无 NUL 字节，并能被随包 Lua 5.1 `loadfile` 加载，否则 fail-closed。
- 分发：`export_presets.cfg` 的 `include_filter` 含 `src/tools/*`，工具随导出进入 PCK。

### 失败策略（fail-closed）

- 工具缺失、清单/SHA256 不符、超时、退出码非 0、输出异常或加载校验失败，任一文件失败即整次后处理失败，不交付半混淆包。
- 失败时新 zip 只写过临时文件，失败即删除；Sharp 原始 zip 改名为 `<输出名>.zip.unobfuscated`，不保留预期文件名的成品，并在冲突/日志列表给出失败脚本、原因与备份文件名。
- 混淆开启但未生成 mod zip（未配置 Sharp 或打包失败）：冲突/日志列表明确「未生成 mod zip，混淆未生效」。

### 设计决策与替代方案

- **Prometheus + 随包 Lua 5.1**：Windows 无现成可离线的源码级混淆器；Prometheus 是纯 Lua 5.1 源码→源码、可固定版本随包分发，且保留全局名（输出依赖 `getfenv`，LuaSTG 的 LuaJIT 提供）。替代方案 `luac` 5.1 字节码被 LuaJIT 拒绝，LuaJIT `-b` 字节码与版本/GC64 耦合，均不采用。
- **固定 NoCff + `Seed=42`**：Weak（含 Cff）在 LuaJIT 下约 44KB 源即触发 `control structure too long`，Medium 的体积/常数上限不可用；NoCff 在 384KB 源上仍可加载，`Seed>0` 让输出确定、可复现。不提供档位选择，避免把不安全的组合暴露给用户。
- **内存条目级改写 zip**：解压到磁盘再压缩会规范化反斜杠条目名并改变顺序；内存逐条目重建可保条目名、顺序与二进制字节不变（实测 PNG 与二进制 sha256 不变）。
- **fail-closed 而非跳过失败文件**：半混淆包会让部分脚本保持原文或缺失，用户难以分辨；宁可保留原始 zip 并显式报错。
- **运行期释放而非直接执行**：PCK 内文件不能直接作为子进程执行，因此释放到 `%TEMP%/AutoCMEX/tools/<bundleHash>/`；固定版本 + SHA256 校验 + 不联网，保证可复现与供应链可控。
- **备选降级（未采用）**：外部命令钩子（由用户自备混淆器），不内置二进制；本批采用内置固定版本。

### 已知边界

- 仅支持 Lua 5.1 语法；含 `goto`/label 等 LuaJIT 扩展语法的脚本无法解析，导出 fail-closed 并指出文件。
- 混淆不是加密：输出仍是纯 Lua 5.1 源码，只提高阅读门槛，存在反混淆工具。
- 体积增大约 2.3 倍（实测 384KB → 895KB 仍可被 Lua 5.1 与 LuaJIT 加载）；一个 `.lua` 一个子进程，单文件启动开销约数百毫秒。
- 真机验收仍待执行：LuaJIT 下 `getfenv` 语义、加载与性能、中文串显示、Sharp 产物可读、杀软误报。

### 实现落点

- `src/core/merge/ModPackageFinalizer.cs`：zip 后处理（混淆 + 工程文件条目控制 + fail-closed 备份）。
- `src/core/merge/PrometheusLuaObfuscator.cs`：工具清单校验/释放与子进程混淆，生产实现。
- `src/core/merge/ILuaObfuscator.cs`：混淆器抽象；测试注入 fake，不依赖真实二进制。
- `src/ui/merge/MergePanel.cs`：Sharp 打包成功后调用后处理，并把结果以 `[混淆]` 行追加到冲突/日志列表。

## 工程纪律与已知旧账

本节收口四类跨模块、容易复犯的纪律与仍未清的旧债；判定依据是 `docs/engineering-guidelines.md` 的规则 18/19/20/21/22/25/30。

### 列表级绑定不覆盖元素级

- **现象**：`AutoList<T>.Bind().OnModify(...)` 只在集合自身增删时触发；元素内部的 `AutoValue<T>` 变化（改启用、改名、改地址、标记删除）不会让列表对象发生任何变化。
- **纪律**：凡是「元素字段也会变」的列表，必须为每个元素逐项订阅 `AutoValue<T>.Bind().OnValue(...)`，并在列表增删时随 `OnModify` 重建这批元素级订阅：先 `Dispose` 旧订阅再挂新订阅（规则 20）；重挂期间抑制订阅回放（否则每次增删都会按「元素数 × 字段数」炸出一串刷新）；绑定回调只调度 `CallDeferred`，不直接碰控件（规则 19）。
- **先例**：目标群 `TargetGroup`（信息页「一键转发」可用态与设置页行回填各自订阅「启用 / 群 ID / 群名」）、AI 模型 `AiModelConfig`（下拉项可用态与标签）、符卡 `SpellCard`（`BossDataWatcher` 把一次猜测通知到两张表）、创作者包 `CreatorPackage.IsDeleted`（删包后驱动包列表重建，不再手动刷新）。
- **GIF 集摘要**：`GifSetRecord` 的活动集字段（`SetName` / `ImportedAt` / `EntryCount` / `RootPath`）已逐项绑定；同一文件夹重复导入是原地更新记录，字段变化会触发摘要与卡片重建（同帧多次变化经排队合并为一次）。

### UI 刷新与事件

- **数据 → UI**：一律由 Sync 绑定驱动（规则 18），绑定回调里只调度 `CallDeferred`（规则 19）；绑定在 `_ExitTree` 全部释放（规则 20）。
- **栏位 → 面板**：子栏不持有发布回调，而是抛事件——`IGifSetPanel` / `IGuessingTablePanel` / `ICreatorRemainingPanel` / `IActivityRulePanel` 的 `PublishRequested`，猜测表另有 `TableChanged`；由信息面板订阅后统一编排串行发布与防抖推送。四栏都是 `InfoPanel.tscn` 的场景内实例，依赖（`DataManager` / `InfoDataService` / `BossDataWatcher` 等）由信息面板经 `IProvide` 统一提供；接口同时暴露 `SetPublishBusy`，让面板把「发布中」忙碌态回灌给栏位（事件同步派发，栏位自己判断不出在飞区间）。
- **在飞护栏**：信息面板按 `PublishItemKind` 记录在飞的单栏发布（`_publishingKinds`），重复触发直接丢弃；在飞期间经对应栏的 `SetPublishBusy` 把该栏发布按钮置灰，收尾与异常路径都在 `finally` 复位。「一键转发」与自动推送仍走 `_isPublishing`，两条链互不影响。
- **日志注入（已清）**：服务与面板改为显式注入 `ILog`（`DataManager.GetLogger(module)` 按模块名取、保留日志模块筛选），`AppLogs` 静态入口只保留在 `Main.cs` 启动层与 `MainWindow` 的一次 bootstrap。

### 弹窗与计时器归属场景

- **一律进场景**：所有 `FileDialog` / `AcceptDialog` / `PopupMenu` / `Godot.Timer` 都是所属面板 `.tscn` 里的常驻节点（`unique_name_in_owner` + `[Node("%…")]` 接口注入），不再在代码里 `new` 后 `AddChild`。生命周期归面板：组件/服务只负责填充内容、弹出与启停，不 `AddChild`、不 `QueueFree`（`Dispose` 只退订信号并把节点隐藏，且退订前用 `GetTargetObj<GodotObject>() + IsInstanceValid` 双检，节点可能先于组件释放），因此面板重新解析后可复用同一对节点。先例：`InfoPanel.%AutoPublishTimer` / `%ReportDialog`、两表栏的 `%TableImageMenu` / `%TableImageMessage`、`MergePanel.%ImportPackageDialog`、`SettingsPanel.%InfoMessageDialog`、`GifSetPanel` 的导入与录制对话框及 `%RecordingRunPanel`。
- **title 与 mode 必须成对**：`FileDialog` 的 `title` 必须同时写 `mode_overrides_title = false`，否则加载时会被 `file_mode` 重写成英文默认值（如 `Open a File` / `Open a Directory`）。
- **Access 写枚举整数**：`.tscn` 里 `FileDialog.Access` 是枚举整数值——`Filesystem = 2`（不要写 `1`，那是 `UserData`）；`file_mode` 同理用整数（`OpenFile = 0`、`OpenDir = 2`）。
- **chrome 例外**：对话框自带按钮（`AcceptDialog.AddButton` 创建的「取消录制」「只重试失败项」）不写进场景，属对话框 chrome 例外；其余结构与文案一律进场景。

### 测试纪律

- UI 测试用 `FakeNodeTree` + `FakeDependency` 搭假场景，不实例化完整场景；只有需要真实 AutoInject 链路（动态实例化子面板、面板级接线、`.tscn` 里的节点引用与依赖提供）的用例才加载真实场景。
- **优先「写模型 → 等帧 → 断言」**：从 `DataManager` 的模型写入触发流程，`await` 到 `process_frame` 后再断言控件；不在测试里手动调 `Refresh()` 抄近道——绑定回放与 `CallDeferred` 都排在消息队列里，等帧是链路的一部分。
- 不为跑绿改断言、不绕过绑定路径：断言表达的是用户可见行为，链路坏了修链路。

### 整合导出选项的实现边界

- **冲突自动改名（实验性）**：开启后同时改写工程内引用与物理文件落盘（工作目录与输出目录都复制改名后的文件），导出的工程与产物保持一致；仅覆盖「多个创作者包内同名资源文件」的自动改名，模板资源同名与对象/定义名冲突不自动改名。
- **按创作者分组**：仅提取式合并生效；按顶层文件夹整搬时资源与对象随包内顶层文件夹整体搬运，该开关在界面置灰并给出悬停说明。

### 已知旧账（未清）

- **少量测试仍手动刷新**：多数「改完模型手动 `Refresh`」的用例已改为「写模型 → 等帧 → 断言」；剩余几处是面板确无绑定路径（替换列表实例、嵌套别名列表、进页清空提示、依赖 `MergeConfig.SharpEditorPath` 的按钮态）或固定帧等待，已就地注释。
- **规则未落自动守护**：规则已迁入 `docs/engineering-guidelines.md`，按约定暂不引入 analyzer/CI 守护，新代码靠评审拦。
- **设置板块仍有空类别页**：左侧 7 个类别里「猜测」「整合」「帮助」3 页仍为空占位（「AI 模型」「群聊」「信息」「通用」4 页已实现）。
